# 針對 FloorSet 競賽問題的研究與方案建議

這個競賽本質上不是傳統意義上「從零開始」的 floorplanning；它更像是一個**帶有硬約束與關係約束的結構化預測問題**。由 entity["company","Intel","semiconductor company"] 釋出的 FloorSet / ICCAD 2026 Problem C 目前公開規格顯示：競賽使用 FloorSet-Lite 的 100 萬筆訓練資料、100 筆 validation、100 筆 hidden test；每個 testcase 的 block 數介於 21 到 120；固定外框被移除、座標可用浮點、aspect ratio 被放寬；真正的硬約束是**不可重疊、soft block 面積誤差在 1% 內、fixed-shape / preplaced block 的尺寸與位置必須精確**，而 soft constraint 只剩 **grouping、MIB、boundary**。官方 README 也明確給出競賽 cost、runtime 因子與 infeasible=10 的規則。這些內容與你上傳的規格摘要相互一致。 fileciteturn0file0 fileciteturn0file1 fileciteturn0file2 citeturn3view0turn4view0

## 競賽本質與真正難點

對這題最重要的判斷是：**這題非常偏向 offline / supervised / imitation，而不是純線上 RL。** 原因不是口號，而是結構本身：你手上有 100 萬筆近最佳解的標註資料，validation 與 hidden test 又是同格式、同 block-count 範圍的資料；官方甚至直接提供可微分 training loss 範例，明顯鼓勵 data-driven 方法。反過來說，官方也明講那個 differentiable loss **沒有包含 fixed、preplaced、MIB、cluster/group、boundary constraint**，它只是近似競賽目標，不能直接拿來當最終解法；如果你只做座標回歸或只最小化那個 loss，很容易 validation 看起來不差，但正式評分因為 constraint 處理不完整而失分。 citeturn4view0turn3view0turn3view2

第二個決定你方法選擇的事實，是**大 case 幾乎決定整個排行榜**。你上傳的官方說明指出 validation / hidden test 是 21 到 120、每個 size 各一題；而目前 README 使用的是依 block count 的**指數加權平均**。如果照公開公式直接計算，單獨 `n=120` 那一題大約就佔總權重的 **63.2%**，`n=116~120` 五題合起來大約佔 **99.3%**。這代表你的方法設計不應該追求「全尺寸平均漂亮」，而應該明確偏向：**大尺寸 instance 的穩定可行性、group / MIB / boundary 處理、以及少量但有效的 test-time search**。同時，speed-up 的好處被 `max(0.7, RuntimeFactor^0.3)` 封頂在 30%，但慢仍會被持續處罰；換句話說，**為了可靠性多花幾秒是值得的，為了再快一點而犧牲可行率則通常不值得**。 fileciteturn0file0 citeturn4view0

第三個關鍵是，這題比很多經典 fixed-outline floorplanning benchmark **更容易學、但更難合法化**。容易的部分在於：沒有固定 canvas、允許 floating-point、aspect ratio 被放寬，這使得連續式模型、生成式模型、甚至直接預測 `(x,y,w,h)` 都比傳統 fixed-outline setting 好做。難的部分則在於：grouping、boundary、MIB 都是**關係型 constraint**，preplaced / fixed-shape 又是**精確型 constraint**，再加上 pin-to-block HPWL 與 bounding-box area 共同決定品質，單純把 netlist rasterize 成影像再做 CNN，通常會比圖模型更吃虧。更進一步，FloorSet 的解本身存在平移、鏡射、群組內對稱等多模態性，若你不先做 target canonicalization，直接回歸絕對座標通常會很抖。 citeturn4view0turn3view2

## 文獻與開源實作地圖

過去幾年的相關工作大致可以分成四條脈絡。第一條是以 entity["company","Google","technology company"] 為代表的 RL 路線：Nature 2021 的 *A graph placement methodology for fast chip design* 把 chip floorplanning / macro placement 表述成 RL，搭配 edge-based GCN，並主張在數小時內產生接近甚至優於人工的解；之後的 Circuit Training 開源 repo 延續這條路，並明確把 pre-training 視為品質與穩定性的關鍵步驟。然而，來自 entity["organization","TILOS AI Institute","research institute"] 與 entity["organization","University of California, San Diego","public research university"] 的後續公開評測則指出，使用更強的 SA baseline 與完整後端評估後，仍有關於 reproducibility、scalability、pre-training methodology 的未決問題；他們的 MacroPlacement repo 也把這整套評測流程公開了。這條文獻脈絡提供了一個重要結論：**RL 能做，但非常吃訓練資源、環境工程與 pre-training 分佈管理，並不天然適合單卡學生專案**。 citeturn10view0turn14view0turn13view1turn13view2

第二條是**圖神經網路與 graph-conditioned floorplanning**。這一支裡面，*Learn to Floorplan through Acquisition of Effective Local Search Heuristics* 不直接生成 floorplan，而是讓 agent 在 sequence-pair 的鄰域中學「哪個 local move 比較值得做」，這很值得借鏡，因為它說明了 RL 不一定要負責整個構造過程，也可以只學 heuristic。之後 *GoodFloorplan* 把 GCN 與 RL 結合成 end-to-end 框架，*GraphPlanner* 則走 variational GCN 路線，主打從電路連接學出到實體佈局的優化映射並用高效率 inference 出解；DAC 2022 的 *Floorplanning with Graph Attention* 與 2024 的 *Edge-aware Graph Attention Network + Hindsight Experience Replay* 則把重點放到更好的 netlist graph encoding 與更穩的 RL 訓練。這些工作共同支持一件事：**對於含連接、pin、group、MIB 這類高關係性的 floorplanning，圖模型幾乎是預設選項，而不是可有可無的 embellishment。** citeturn10view5turn15search11turn18search1turn8search1turn18search6

第三條是**結構化表示與建構式 decoding**。KDD 2022 的 *Generalizable Floorplanner through Corner Block List Representation and Hypergraph Embedding* 很重要，因為它不是把 block 直接放到大座標格上，而是利用 CBL 這種 floorplan representation 把 action space 壓小，並用 hypergraph embedding 處理多端連接，核心思想是：**把「合法 floorplan 的 combinatorial structure」直接放進表示法，而不是事後再補救。** 2025 的 *Learning placement order for constructive floorplanning* 與 2026 的 *MdpoPlanner* 又把問題往前推一步：它們明說**placement order 本身就是要學的**，而不是手工規則；後者更進一步用 mask-driven constructive floorplanner 來確保 legality，並報告對 MCNC / GSRC 的顯著改善。雖然這些 benchmark 比 FloorSet 小得多，但對你這題最有價值的不是 benchmark 數字，而是三個設計概念：**order learning、representation-induced legality、以及先天可修復的 constructive state**。 citeturn27search5turn27search11turn22view0

第四條是**生成式與解析式／可行化方法**。ICML 2025 的 *Chip Placement with Diffusion Models* 很值得重視：它直接點名 RL 常見問題是 sample inefficiency 與 per-circuit online training，改用 diffusion 離線訓練、zero-shot 產生 placement，並用 guided sampling 改善 legality 與 HPWL；作者也公開了 chipdiffusion repo。與此同時，解析式與可行化方法並沒有死掉：2021 的 QinFer 用 hypergraph bipartition 先產生 distributed floorplan，再用 quasi-Newton legalize；2024 的 Per-RMAP 把 floorplanning 重寫成 feasibility-seeking + superiorization，能處理 I/O assignment、soft modules，並在若干 benchmark 上以接近最優的 wirelength 換到極大速度優勢；2025 的 CSF 則以 nonsmooth analytic model + Q-learning assisted conjugate subgradient 抗 local convergence。這表示對 FloorSet 這種 constraint 多、合法性很重要的題目，**生成器與解析式 legalizer 的混合**通常比「純神經網路一次吐出最終答案」更務實。 citeturn11view0turn11view1turn34view0turn25view3turn25view1turn26view0

從公開 repo 角度看，我查到最值得直接拿來借元件的有：官方 FloorSet repo 與 evaluator；Circuit Training 與 MacroPlacement 這組可拿來理解 RL / proxy cost / benchmark flow；MaskPlace 與 ChiPFormer 這組可拿來借 visual mask、offline RL、dataset pipeline；chipdiffusion 可借 diffusion backbone、guided sampling、PyG graph data format；FlexPlanner 所在的 EDA-AI repo 可借 multi-modal / hybrid-action 設計經驗；CORE 則是目前相對新且公開的 floorplanning EA+RL 框架；此外，DREAMPlace 與 entity["organization","The OpenROAD Project","eda consortium"] 的 Hier-RTLMP / macro-placement 元件很適合被當 refinement / legalization /後處理工具，而不必把它們整套當主方法。值得注意的是，我在查到的官方／作者來源中，**真正直接對應「公開 floorplanning code」的 repo 比 placement code 少很多**；也就是說，你最後多半還是要自己把 floorplanning representation、constraint repair、以及 FloorSet evaluator 綁起來。 citeturn3view0turn14view0turn20view0turn20view1turn20view2turn34view0turn35view0turn31view2turn31view0

## 我最推薦的解法

綜合題目結構、文獻成熟度、開源可重用程度、以及你手上的 **單張 L4 24GB + 一台 64-core CPU server**，我不會把「純 RL from scratch」放進前三名。我認為最值得做的，是**把學習模型當成高品質初始化器或可行建構器，再用精確 repair / local search 把它推到競賽 scoring 需要的合法區域**。下面三個方案，是我認為對你最有機會的排序。

### 約束感知的圖式建構式模型

如果你只能做一個，我會選這個。核心做法不是直接回歸整個 `(x,y,w,h)`，而是把問題拆成**圖編碼 + 建構式解碼 + 精確 repair**。輸入圖應該至少含：block node、pin node 或 pin-feature、b2b connectivity、p2b connectivity、group / MIB / boundary / fixed / preplaced 標記；其中 same-group / same-MIB 可以作為 edge type 或 constraint node。解碼端不要直接在連續座標空間瞎猜，而要用類似 CBL / B\*-tree / skyline / maximal-empty-rectangle 的**可構造表示**，讓 block 逐步落位，並用 mask 保證不重疊。shape 參數不要直接預測 `w,h`，而要預測一個 logarithmic aspect code `r`，再用 `w=sqrt(A·e^r), h=sqrt(A/e^r)` 讓 soft block 天然滿足面積；fixed / preplaced block 直接 clamp 到目標尺寸，MIB group 共享 `r` 或共享 shape head；grouping 則先把 group 內部打包成局部子問題或 supernode，再展開成連通小版圖。這套想法和 sequence-pair local-search、CBL + hypergraph、GraphPlanner、GAT / EAGAT、以及 recent order-learning work 的精神是一致的，但更貼近 FloorSet 的 constraints 與 scoring。 citeturn10view5turn27search5turn18search1turn18search6turn22view0turn4view0

它最強的地方有三個。第一，**可行率最高**：大部分合法性在 decoding / repair 階段就被處理掉，而不是靠 loss 希望模型「自己學會」。第二，**最符合你的硬體**：120 個 block 的圖其實不大，L4 很足夠訓練中型 GNN + Transformer decoder；真正吃時間的是資料前處理、beam search、以及 large-case 的 local refinement，而這剛好可以丟到 64-core CPU server。第三，**最適合這個評分**：因為你可以做 size-aware inference，例如 `n<100` 只跑 greedy + 小 beam，`n>=110` 才開 8 到 32 條 beam、做 group-aware swap、boundary repair、短局部搜尋。它的主要缺點是工程量不小，尤其 target canonicalization、group supernode unpacking、以及 preplaced / boundary 的對齊策略需要設計；但就「競賽成功率 / 研究風險 / 你目前硬體」三者取平衡，這仍然是我心目中的第一名。我會估：**一到兩週可做出第一個能交差的版本，三到五週能做出有競爭力的版本**；先用 10 萬到 30 萬筆訓練，穩定後再放大到 50 萬以上，而不是一開始就硬吞 100 萬。這也是三個方案裡，我最看好能在你條件下真正落地的。 fileciteturn0file0 citeturn4view0

### 圖條件擴散與流匹配生成器

這是我排第二名、但**理論天花板可能最高**的路線。它的吸引力很明確：你手上有大量近最佳解，task 又是多模態結構預測；diffusion / flow matching 對這種問題天然有優勢。ICML 2025 的 chipdiffusion 已經證明，graph-conditioned diffusion 可以離線訓練、對未見實例 zero-shot 產生 placement，並透過 guided sampling 同時改善 legality 與 HPWL；官方 repo 也公開了 small / medium / large 模型訓練、fine-tuning 與多樣本 guided evaluation 的流程。更進一步，2026 的 FlowPlace 嘗試用 flow matching 來降低 diffusion 的 sampling 成本、減少 overlap 與對 gradient-based legalizer 的依賴，這對你只有單張 L4 的情境特別有吸引力，因為**你最缺的不是模型容量，而是 test-time sampling budget 與訓練天數**。就競賽題目本身而言，組合方式我會建議做成：**graph encoder + coarse生成 + guidance + exact repair**，而不是完全端到端。group / MIB / boundary 這些 constraint 不要全丟給 denoiser 學，而是讓 guidance 與 repair 負責最後一公里。 citeturn11view0turn11view1turn34view0turn1search18

我把它排在第二，不是因為它不強，而是因為它對你來說**成本更高、成功條件更多**。第一，diffusion 需要你先處理 label symmetry 與 target normalization，否則 denoising 目標本身會糊掉。第二，它雖然可以同時吐出整體佈局，但 hard constraint 尤其是 fixed / preplaced 的 exactness、以及 group connectivity，仍然很可能要靠後處理。第三，sampling runtime 是現實問題；雖然競賽的速度收益有上限，但若你每個 large case 要跑太多 denoise steps 或太多 candidate sample，一樣會被 runtime 拖累。實務上，我會把它當「在第一名方法穩定後衝天花板的第二階段」，而不是一開始就 all-in 的唯一方案。我會估：**兩到三週做出 prototype，四到八週才有機會做出夠穩的競賽版**；若你真的走這條路，建議先用 small / medium model、10 到 20 step sampler、8 到 16 candidate samples 起步，並把 large-case 的 sample ranking 交給精確 evaluator 或 learned ranker。這條路非常值得研究，但不應該先於第一名方案。 citeturn34view0turn11view1turn4view0

### 學習暖啟動加解析式搜索

這是我排第三名，但它是**最穩的備胎**，而且如果競賽時間很緊，它反而可能是最划算的。它的核心思想很簡單：不要讓 learning model 直接獨立完成 floorplanning，而是只負責提供**好的初始化、move score、或 candidate ranking**；真正把解推進合法區域與低 cost 區域的，是 QinFer / Per-RMAP / CSF / B\*-tree SA / 小型 EA 這類更可控的搜索器。你可以甚至從官方 B\*-tree SA template 直接起步，把 model 接在三個地方：一是預測 block order、二是預測 group / MIB 的初始化 shape、三是做 move acceptance 的 learned critic。若你願意再多做一步，CORE 的想法也很值得借：不用把整套 EA+PPO 全搬過來，但它證明了「**RL / learned policy 負責局部引導，EA / search 負責全域探索**」是有效的 floorplanning 方向，而且現在已經有公開 C++ backend + pybind11 的 repo 可以參考。再加上 DREAMPlace 與 OpenROAD 的 macro-placement / legalization 組件，你其實很容易拼出一個**能跑、能修、能並行**的競賽系統。 citeturn25view3turn25view1turn26view0turn35view0turn31view2turn31view0turn4view0

它排第三，原因是天花板通常低於前兩者，因為你沒有真的把 100 萬筆最佳解 fully exploit 掉；但它的優勢非常明顯：**最容易 debug、最容易保證可行、最能善用 64-core CPU server、也是最容易在短時間內做出穩定 submission 的方法。** 對 FloorSet 來說，我很推薦把它設計成「雙系統保險」：先有一個學習生成器，再準備一個這樣的 search-based legal fallback。若 large case 的生成器出現 grouping 斷裂、boundary 沒碰到、或 preplaced 偏掉的情況，就自動切到 search/refine 流程。從時間與資源看，這條路**一週左右可做出可靠 baseline，兩到三週可做出相當不錯的版本**；若你最後選擇第一名方法，它也很適合作為第一名方法的後處理與保底。 citeturn4view0turn35view0

## 依你的硬體如何落地

你的 **Mac mini M4 16GB** 最適合做資料檢視、可視化、canonicalization、單 case debug、與小模型原型；真正的主訓練與大規模 validation，應該全部放到 GPU / Linux server。原因不是抽象地說「GPU 比較快」，而是你會借到的幾個關鍵 repo 幾乎都把環境鎖在 Linux/CUDA：Circuit Training 需要 TF-Agents、DREAMPlace binary 與 placement cost binary；ChiPFormer 的公開環境仍以舊版 PyTorch + DGL + CUDA 11.3 為主；CORE 直接提供 Linux `g++` / pybind11 build flow；chipdiffusion 也預設 conda + CUDA + hMETIS / shmetis 類依賴。換句話說，**Mac 不是不能做，而是不適合作為主戰場**。你最理想的配置是：Mac 負責開發與可視化；L4 server 負責模型訓練與 inference；64-core CPU server 負責大規模 candidate scoring、beam / local search、以及 validation 全掃。 citeturn14view0turn20view1turn35view0turn34view0

在這個硬體前提下，我會很務實地安排：先用官方 evaluator 跑通 baseline，立刻建立 `--save-solutions` / `--score` / `--validate` 的迴圈；然後優先做**大 case 專用策略**，因為公開 scoring 幾乎把勝負都壓在最大幾個 instance 上。具體做法是：第一週把 data loader、visualizer、constraint checker、canonicalization 與 baseline 全接通；第二到三週完成第一名方案的 graph encoder、constructive decoder 與 repair；第四週做 beam / restart / local-search time budget tuning；如果第四週末第一名方案已經穩，再決定要不要把第二名的 diffusion 版當 boost。這樣做的重點不是保守，而是符合公開規格：validation / hidden test 同格式、官方 evaluator 可重評分、速度收益有限、而 infeasible 的代價又極高。 citeturn4view0

## 最終判斷

綜合文獻、公開 code、競賽 scoring、以及你的硬體條件，我的最終排序是：**第一名，約束感知的圖式建構式模型；第二名，圖條件擴散與流匹配生成器；第三名，學習暖啟動加解析式搜索。** 如果我是你，我會把第一名當主線，第三名當保底與後處理，第二名則當作在主線穩定之後再衝上限的加分項。相反地，我**不建議**你把時間主要投入在純從零 RL、或直接移植 Circuit Training 式流程：它在研究上重要，但對這個有 100 萬筆近最佳標註、又把勝負壓在超大 case 的 FloorSet 競賽來說，不是你目前資源下的最佳風險報酬比。最能贏這題的，不是最「酷」的方法，而是**最能把圖結構、表示法、合法性修復、與大案例 test-time budget 這四件事同時做好的方法**。 citeturn4view0turn11view0turn13view1
